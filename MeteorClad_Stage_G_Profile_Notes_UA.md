# MeteorClad — Stage G: System profiling

## Мета

Stage G додає деталізацію до Stage F benchmark, щоб відрізнити вартість ігрового оновлення від витрат на подання графічних команд. Бойові механіки, частоти оновлення та поведінка ворогів не змінюються.

## Профільовані секції

| Секція | Що вимірюється |
|---|---|
| frame_dt | Frame delta, який LÖVE передає в update |
| game_update_total | Повний виклик Game:update(dt) |
| player_update | Player:update(dt) |
| enemies_update | Enemies:update(dt), включно з AI та контактними перевірками |
| projectiles_update | Projectiles:update(dt), включно з перевірками зіткнень |
| loot_update | Loot:update(dt), включно з перевірками підбирання XP |
| draw_total_cpu | CPU-час усіх draw-секцій у love.draw |
| *_draw_cpu | CPU-час подання команд кожної графічної підсистеми |

Для кожної секції записуються average, P95 і maximum у мілісекундах.

## Файли та керування

- На Android кнопка **TEST** у нижньому правому куті відкриває панель; на ПК — **F6**. Android-меню використовує сенсорні кнопки.
- 1–6 запускають ті самі шість сценаріїв Stage F.
- Після тесту Stage F продовжує записувати stage_f_benchmark_results.csv.
- Stage G додає окремий рядок до stage_g_profile_results.csv у save directory LÖVE.
- **O** відкриває save directory.
- **C** копіює шлях до Stage F CSV.
- **P** копіює шлях до Stage G profile CSV.
- **Esc** очищає benchmark-сцену та закриває панель; на Android це робить сенсорна кнопка BACK / CLOSE.\n\nНа Android touch UI запускає benchmark, але не замінює клавіатурний рух гравця у звичайному режимі.

Обидва CSV append-only. Після завершення тестів копіюйте їх у benchmark-results/ для Git.

## Важливі обмеження

1. Для вимірювання використовується love.timer.getTime(); кожна секція має невелику ціну виклику таймера. Профіль — діагностичний, а не безкоштовний.
2. draw_*_cpu вимірює CPU-час подання команд LÖVE. GPU може виконувати роботу асинхронно; ці значення не є GPU execution time.
3. game_update_total охоплює підсистеми update та іншу логіку Game:update; не слід підсумовувати його з дочірніми секціями.
4. draw_total_cpu охоплює підсистеми draw; не слід підсумовувати його з дочірніми draw-секціями.
5. Stage F uncapped baseline залишається окремою контрольною серією. Через додаткові вимірювання Stage G його FPS не можна прямо порівнювати зі Stage F.
6. Після runtime-перевірки на цільовій машині слід зробити щонайменше три профільні проходи підозрілих сценаріїв, перш ніж змінювати алгоритми або структури даних.
