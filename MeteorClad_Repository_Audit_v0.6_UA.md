## 1. Призначення

Цей документ продовжує історичний технічний огляд v0.5. Попередній документ не переписується: він описує початковий однофайловий прототип. Цей аудит фіксує стан репозиторію після стабілізації та модульного розділення.

Репозиторій: https://github.com/Skalagrimmo/MeteorClad

## 2. Підтверджений стан репозиторію

У корені є десять Lua-файлів:

| Файл | Відповідальність |
|---|---|
| `main.lua` | Точка входу, створення контексту, LÖVE callbacks |
| `config.lua` | Арена та прототипи ворогів |
| `utils.lua` | Математичні утиліти |
| `player.lua` | Стан і механіки гравця |
| `enemies.lua` | Створення ворогів, AI, шкода, смерть |
| `projectiles.lua` | Снаряди, зіткнення, відбиття |
| `loot.lua` | XP-сфери та підбирання |
| `upgrades.lua` | Пул покращень |
| `game.lua` | Стани гри, хвилі, level-up, введення |
| `ui.lua` | HUD та екрани стану гри |

### 2.1. Архітектура контексту

У `main.lua` формується таблиця `ctx` з посиланнями на конфігурацію, утиліти та менеджери. Модулі отримують її через `:bind(ctx)`.

Послідовність прив'язування: Loot, Projectiles, Enemies, Player, Game, UI. Це зменшує потребу в циклічних імпортах і робить залежності явними. Контекст є спільним контейнером посилань, а не окремою ECS чи системою подій.

### 2.2. Поточний ігровий цикл

Збережено арену 800×600, хвилі ворогів, чотири базові типи противників, melee-атаки, Вихор, Dash, відбиття снарядів, XP-сфери та вибір покращень із трьох карток. HUD має шкали HP, XP, Dash і Вихору.

Назва вікна у поточному `main.lua`: `MeteorClad - Hack'n'Slash RPG (Modular v0.6)`.

## 4. Додаткова перевірка стабільності: Game Over та level-up

### Виявлений ризик

У попередній реалізації `Game:update(dt)` послідовно викликала оновлення ворогів, снарядів і XP-луту. Смертельне зіткнення могло встановити `gameover`, але в тому самому кадрі наступна система збору XP могла викликати `triggerLevelUp()` і замінити стан на `levelup`.

### Патч у гілці стабілізації

Після кожного виклику підсистеми `Game:update(dt)` повторно перевіряє `self.state`. Якщо стан більше не `playing`, функція завершується.

Це зберігає пріоритет завершального стану:
- смертельна шкода не дозволяє продовжити обробку до підбирання XP;
- перехід у `levelup` припиняє обробку хвилі в цьому кадрі;
- логіка появи наступної хвилі виконується лише поки гра лишається у стані `playing`.

## 5. Відкрите дизайнерське питання: усі перки досягли maxRank

`Game:triggerLevelUp()` формує список доступних покращень за умовою `currentRank < upg.maxRank`. Якщо список порожній, функція повертає гру до стану `playing` без картки вибору. Оскільки рівень і XP-поріг уже змінені, гравець може отримати рівень без винагороди.

Це не варто вирішувати випадковим бонусом без дизайнерського погодження. Потрібно окремо обрати правило:
1. додати нескінченний/повторюваний малий бонус;
2. запропонувати альтернативну універсальну винагороду;
3. дозволити певним перкам перевищувати поточні ранги;
4. або завершити звичайну прокачку іншим способом.

До прийняття рішення не додавати приховане автоматичне збільшення характеристик.

## 6. Інші технічні зауваження

- `run.bat` містить абсолютний шлях `C:\Program Files\LOVE\love.exe`. Це підходить для конкретної машини, але зменшує переносимість репозиторію.
- README раніше мав незакритий fenced code block. У гілці стабілізації його структуру виправлено та доповнено описом модулів і документації.
- Вороги поки не мають взаємного розштовхування. Не вважати це помилкою без перевірки бажаної поведінки натовпу.
- Не додавати оптимізацію `dist2()`, просторове розбиття або fixed timestep без вимірів, що підтверджують потребу.

## 7. Наступний план робіт

### Stage A.1 — стабілізація та регресійна перевірка
1. Перевірити сценарій: XP вистачає на кілька рівнів — гравець послідовно обирає покращення, не підбираючи нову сферу.
2. Перевірити смертельну контактну шкоду, смертельний снаряд та наявність XP-сфери поруч у момент смерті.
3. Переконатися, що стан `gameover` не змінюється на `levelup`.
4. Перевірити максимальні ранги перків і випадок, коли весь пул вичерпаний.
5. Перевірити повний reset після натискання R: вороги, снаряди, XP, рахунок, хвиля та ранги.
6. Вирішити, якою має бути винагорода, коли всі перки досягли максимуму.

### Stage B — бойова перевірка та баланс
1. Перевірити кожен тип ворога окремо та у змішаних хвилях.
2. Перевірити melee, Вихор, splash і відбиття снарядів.
3. Перевірити, що нагорода за смерть ворога видається рівно один раз.
4. Перевірити кулдауни до та після перків.
5. Перевірити читабельність HP-індикаторів і телеграфів атак.

### Stage D — розширення світу
1. Відокремити світові координати від координат екрана.
2. Додати камеру та коректне перетворення координат для миші.
3. Додати масштабування/зміну розміру вікна та перевірити HUD у screen-space.
4. Розширити арену за межі екрана.
5. Додати колони й перешкоди як об'єкти світу з перевіркою зіткнень.
6. Після цього переглянути spawn-позиції, рух ворогів та межі камери.

### Stage E — візуальне й аудіо-полірування
Зберегти геометричний стиль прототипу, додати читабельні телеграфи атак і виразні ефекти Dash, удару, парирування, смерті та підбирання XP. Не змішувати заміну примітивів на спрайти з переробкою бойової логіки.

### Stage F — продуктивність
Профілювати 50/200/500/1000 ворогів, інтенсивні снаряди та великі групи XP-сфер. Записувати середній FPS і час кадру. Рішення про оптимізацію приймати лише за результатами тесту.

## 8. Критерії приймання Stage A.1

- [ ] Накопичений XP дозволяє послідовно обрати всі належні level-up.
- [ ] Після смертельної шкоди стан `gameover` залишається незмінним до перезапуску.
- [ ] У тому самому кадрі після смерті не запускається level-up із підбирання XP.
- [ ] Кожен ворог дає очки та XP рівно один раз.
- [ ] Досягнення maxRank не створює карток із уже недоступними перками.
- [ ] Поведінка при повному вичерпанні пулу покращень відповідає окремо погодженому правилу.
- [ ] R запускає чистий забіг.
- [ ] README має коректне форматування та актуальну структуру.

## 10. Локалізація шрифту інтерфейсу

Під час першого запуску на Windows в українських підписах HUD, картках покращень та Game Over відображалися порожні квадрати. Це характерна ознака відсутніх гліфів у поточному шрифті, а не пошкодження UTF-8 у Lua-файлах.

У гілці стабілізації додано завантаження зовнішнього TTF:
- очікуваний файл: `fonts/NotoSans-Regular.ttf`;
- файл створюється користувачем із офіційного static TTF Noto Sans Regular;
- `love.load()` перевіряє наявність файлу та один раз встановлює його через `love.graphics.newFont(..., 12)`;
- якщо файл відсутній або не завантажується, гра продовжує роботу зі стандартним шрифтом і пише попередження в консоль.

Офіційне джерело TTF: https://notofonts.github.io/latin-greek-cyrillic/fonts/NotoSans/hinted/ttf/NotoSans-Regular.ttf
Ліцензія й attribution: `fonts/OFL.txt` та `fonts/README.md`. Noto Sans підтримує кириличні та розширені кириличні набори; розповсюдження можливе за умов SIL Open Font License 1.1.

**Відкрита дія перед повним закриттям дефекту:** додати завантажений TTF у `fonts/NotoSans-Regular.ttf`, підтвердити його в Git, перезапустити гру та перевірити українські тексти в HUD, level-up і Game Over. Сам код завантаження перевірено статично; фактичний рендеринг із цим TTF ще не підтверджено.
